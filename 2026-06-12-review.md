## Significant (re-scope leftovers — should fix before posting) — STILL OPEN

4. **The abstract still describes the pre-re-scope draft.** The re-scope's stated
   intent was "CHUNK is *framing*, not a transport" and "HELLO is identity-only."
   Yet the abstract (line 83) still says **"The DNS CHUNK transport mechanism"** —
   the exact conflation the re-scope swept out of the body. The abstract also still
   advertises the full **"Agent discovery, HELLO handshake, BEAT keep-alives and
   synchronization messages"** framework (lines 27–28) as if this document specifies
   it, even though the body now defers the wire mechanics to chunk-transport. The
   abstract was written for the old scope and never reconciled with the narrowing.
   This is the single most visible inconsistency a reviewer will hit.

5. **Inconsistent normative/informative marker on the chunk-transport reference.**
   chunk-transport is cited **8× as `{{I-D.berra-dnsop-chunk-transport}}` (normative)**
   and **3× as `{{?I-D…}}` (informative)** in the same document. It can't be both.
   Given the body now genuinely depends on CHUNK for the DNS transport ("mandatory to
   support"), it is arguably **normative** — but right now it sits in *neither* the
   `normative:` nor `informative:` YAML block (both are empty, lines 42–44), so
   kramdown is auto-classifying by marker and the mix is silently wrong. STATUS flags
   the chunk-transport dependency as "unresolved but acceptable" for *posting* — but
   the *marker inconsistency* is a real bug regardless of which way that decision goes.
   Same question applies to `dnssec-automation` (cited `?` but it carries the normative
   multi-signer algorithms). **→ Needs an authorial call (normative vs informative),
   then populate the empty YAML blocks accordingly.**

6. **`MessageType field of the CHUNK EDNS(0) option`** (lines 1510, 1515). The
   re-scope moved the CHUNK wire format (including whether there even *is* an EDNS
   option vs. an RRtype carriage) into chunk-transport. This draft now asserts a
   specific structural detail ("the CHUNK EDNS(0) option") that it no longer owns and
   that STATUS's chunk-transport notes describe as **dual-mode** (RRtype *and* EDNS
   option). This over-specifies a field that belongs to the other draft; it should
   describe the message type abstractly and defer the carriage to chunk-transport.

## Post-review structural changes (author-initiated, same session)

These are beyond the original 8-item review — author-driven changes to remove
development-history artifacts and simplify the record model.

### A. `HSYNC3` → `HSYNC` rename — DONE

The `3` in `HSYNC3` was a development-history artifact (the record went
HSYNC → HSYNC2 → HSYNC3 over the author's iteration); it carries no meaning in
the spec. Renamed all 77 `HSYNC3` tokens to `HSYNC`. `HSYNCPARAM` (81 occurrences)
deliberately untouched. The 9 pre-existing bare `HSYNC` tokens (2× "HSYNC-based",
plus references to the old single record inside TO-BE-REMOVED rationale blocks) were
left as-is. Parse exit 0; no `HSYNC3` residue.

### B. "Rationale: Two Records, Not One" block — TRIMMED

Removed the historical framing ("an earlier design used a single HSYNC record…",
the three-bullet "problem one/two/three" scaffolding). Kept the forward-looking
design rationale (the inconsistency-prevention argument + the registry-extensibility
benefit), so the block still shows the two-record split was a considered choice rather
than narrating the iteration history. **Also fixed a substantive error** the author
caught: the old text said "two **Providers** could each publish a record" with
disagreeing values — but Providers do not publish HSYNC/HSYNCPARAM records; the
**zone owner** does (the records live in the owner's zone — the whole premise of the
draft). Reworded so the inconsistency risk is correctly attributed to a (confused)
zone owner. Verified the same Provider-publishes-the-record error does not recur
elsewhere in the document. Block remains under TO-BE-REMOVED (per standing policy).

### C. Remove the HSYNC `State` field (4 fields → 3) — DONE

**Rationale (author).** The HSYNC RDATA had four fields: `State Label Identity
Upstream`. `State` (values ON/OFF) existed for one purpose: to mark a Provider as
being offboarded *without* deleting its HSYNC record, so that data contributed by
that Provider could still be identified and filtered/wound down. That function is now
fully provided by the **presence or absence of the Provider's Label in the HSYNCPARAM
role keys** (`servers=` / `signers=` / `auditors=`). Removing the Label from all role
keys is the offboarding signal; `State` is therefore redundant. HSYNC drops to three
fields: `Label Identity Upstream`.

**Design decision (confirmed with author).** Label-absent = **begin orderly removal**,
not "already gone". The model:

| HSYNC record | Label in a role key | Meaning |
|--------------|---------------------|---------|
| present      | yes                 | active  |
| present      | no (absent from all)| being offboarded — Agents run the orderly remove-signer / remove-NS wind-down; the still-present HSYNC record keeps the Provider identifiable (Label + Identity) during wind-down |
| absent       | n/a                 | gone — owner deletes the HSYNC record after wind-down completes |

This preserves the old `State=OFF` wind-down semantics (RFC 8901 "remove signer" in
correct order) — the "being removed" Provider stays identifiable via its lingering
HSYNC record rather than via a State field.
