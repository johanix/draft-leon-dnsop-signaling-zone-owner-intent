**Date:** 2026-06-06

**Comparison points:** -00.md (published on datatracker 2025-09-04), the

## Severity scale

- **S1 — Load-bearing**: blocks publication; affects technical
  correctness, structural coherence, or whether peer drafts can cite

- **S2 — Significant**: real spec-quality issue (missing definitions,

- **S3 — Polish**: clarity, framing, structure, naming, terminology

## S1 findings (load-bearing)

### S1.1  The draft uses HSYNC; the implementation has HSYNC3 + HSYNCPARAM

**Location:** entire `# The HSYNC RRset` section (lines 459-571) and all
prose references to "HSYNC RRset" throughout the document.

**Description:** The draft defines a single RR type `HSYNC` with five
RDATA fields (State, NSMgmt, Sign, Identity, Upstream). The tdns-mp
implementation already replaced this with **two** RR types:

- **HSYNC3** (type code 65285): per-provider enrollment, RDATA = State,
  Label, Identity, Upstream. *No role fields.*
- **HSYNCPARAM** (type code 65286): zone-wide policy as a list of
  `(key, value)` pairs — SVCB-shaped. The role-like fields (`nsmgmt`,
  `signers`, etc.) live here.

This is the largest single load-bearing item in the draft. The TODO
explicitly calls this out (TODO §"Structural rewrite (do first)").

**Why it matters:** every other dependency on this draft (notably
delegation-mgmt-via-ddns-02 §"Operator coordination via HSYNCPARAM",
which cites `pubkey` by name) assumes the two-RR model. Until the draft
catches up, the sister draft's citation is referring to a record type
that has no presence in the published draft.

**Recommendation:** Restructure `# The HSYNC RRset` into two sections:

1. **`# The HSYNC3 RRset`** — describe per-provider enrollment with
   fields State / Label / Identity / Upstream. Note explicitly that
   HSYNC3 has *no role fields*; roles are expressed in HSYNCPARAM.
2. **`# The HSYNCPARAM Record`** — single RR per zone, SVCB-shaped, list
   of `(key, value)` pairs. Define the registry of keys (see S1.2).

Both records sit at the zone apex. Each subsection that currently uses
"HSYNC" needs to be rewritten in terms of one or the other (mostly
HSYNCPARAM for policy decisions; HSYNC3 for enumerating providers).

### S1.2  HSYNCPARAM keys are not defined anywhere in the draft

**Location:** absent. The draft has no `## HSYNCPARAM Keys` section, no
table of keys, no per-key semantics.

**Description:** The implementation defines eight HSYNCPARAM keys (key
numbers 0-7):

| # | Name | Type | Meaning (per impl comments) |
|---|------|------|-----------------------------|
| 0 | `nsmgmt` | value (`owner`/`agent`) | who manages the NS RRset |
| 1 | `parentsync` | value (`owner`/`agent`) | who handles parent sync |
| 2 | `servers` | comma-list of labels | data-contributing providers |
| 3 | `signers` | comma-list of labels | signing providers |
| 4 | `pubkey` | flag | providers SHOULD publish SIG(0) KEY |
| 5 | `pubcds` | flag | providers SHOULD publish CDS/CDNSKEY |
| 6 | `suffix` | label | DNS label for provider NS+glue |
| 7 | `auditors` | comma-list of labels | auditor providers |

Each needs a normative definition: name, key number, value encoding
(flag / value / list), semantics, default behavior when absent. The TODO
lists six keys (`servers`, `signers`, `auditors`, `nsmgmt`, `parentsync`,
`prefix`) and is missing `pubkey`, `pubcds`. (See S1.3 for the `pubkey`
inconsistency with the sister draft, and S1.4 for the `prefix`/`suffix`
naming confusion.)

**Why it matters:** Per the IANA Considerations approach you took for
delegation-mgmt-via-ddns -02, the registry for HSYNCPARAM keys needs to
be defined here (analogous to the SvcParamKey registry for SVCB). Without
it there is no shared vocabulary for tools, no registration procedure for
new keys, and no way for cross-cite drafts to refer to keys by their
canonical names.

**Recommendation:** Add a new `# HSYNCPARAM Keys` section with:

- An introductory paragraph explaining HSYNCPARAM is SVCB-shaped and that
  keys live in a registry analogous to the SvcParamKey registry.
- One subsection per defined key (8 currently) with name, key number,
  type, semantics, and example.
- A new IANA Considerations subsection requesting creation of the
  "HSYNCPARAM Keys" registry with the initial eight entries.
- Registration procedure (Specification Required, etc.) and a private-use
  range.

### S1.3  `pubkey` (and `pubcds`) are missing from the TODO and the draft, but cited externally

**Location:** absent. `pubkey` is not mentioned in -01.md; it is
referenced in `delegation-mgmt-via-ddns-02.md` §"Operator coordination
via HSYNCPARAM".

**Description:** delegation-mgmt-via-ddns-02 explicitly cites the
`pubkey` key of HSYNCPARAM by name (delegation-mgmt-via-ddns-02 lines
562-570) and refers to its semantics in prose:

> "the child operator's intent that each provider SHOULD publish the
>  child's SIG(0) KEY at `_sig0key.{child}._signal.{their-ns-name}.` in
>  their own zone."

This semantics needs to actually appear in this draft. Without it the
sister draft's `?I-D.leon-dnsop-signaling-zone-owner-intent` reference
resolves to a draft that does not contain the cited concept.

**Why it matters:** Cross-reference soundness for the delegation-mgmt
submission. Identified earlier today as the main blocker for that draft's
Last Call.

**Recommendation:** When defining the eight HSYNCPARAM keys (S1.2),
include `pubkey` and `pubcds` as flag-type keys. For `pubkey`, the
semantics text should be aligned with delegation-mgmt-via-ddns-02 — the
authoritative use case for the key is the SIG(0) KEY publication for
DDNS UPDATE bootstrap. A forward reference to
`?I-D.ietf-dnsop-delegation-mgmt-via-ddns` is appropriate.

### S1.4  Reserved/private use range for HSYNCPARAM keys

**Location:** absent.

**Description:** The implementation reserves key value 65535 as
`hsyncparam_RESERVED` and handles unknown keys with the convention
`keyN` for unknown numeric keys (similar to how SVCB does
`SvcParamKey<N>`). The draft says nothing about how unknown keys are
parsed/displayed, nor whether there is a private-use range.

**Recommendation:** Define a private-use range and the `keyN` convention
for unknown keys in §IANA Considerations.

### S1.5  HSYNC3 has no `Sign` field — but HSYNCPARAM `signers` lists labels

**Location:** S1.1's restructure surfaces this dependency.

**Description:** Per the implementation, HSYNC3 has no Sign field. The
`signers` key in HSYNCPARAM is a *list of labels*. The labels reference
HSYNC3 records by their `Label` field. So "is this provider a signer?"
is answered by: (a) look up the provider's HSYNC3 record by Label; (b)
check whether that Label is in the HSYNCPARAM `signers` list.

The current draft's HSYNC.Sign field cleanly answered this with a single
boolean. The new model requires *two* lookups. The draft needs to
explain this resolution clearly, including:

- How the `Label` field in HSYNC3 is used as an identifier within
  HSYNCPARAM key values.
- Why this indirection is useful (one common reason: a provider may have
  multiple HSYNC3 records with different Identity/Upstream chains, but a
  single role per Label).

**Recommendation:** Add a short section, perhaps `# Linking HSYNC3 and
HSYNCPARAM` or as a subsection of HSYNCPARAM, explaining the label-based
indirection with a worked example.

### S1.6  `Sign` field semantics need to be deprecated/replaced consistently

**Location:** lines 562-572 (`## Semantics of the HSYNC Sign Field`),
plus many examples throughout (~5-7 locations).

**Description:** Under the two-RR model the per-provider Sign field
disappears from HSYNC3. Every prose reference to Sign=SIGN or Sign=NOSIGN
needs rewriting to "the provider is listed in HSYNCPARAM `signers`" or
similar. The "Sign field semantics" section as a whole disappears,
replaced by the HSYNCPARAM `signers` key definition.

**Recommendation:** Remove the `## Semantics of the HSYNC Sign Field`
section. Walk through all examples and update to use HSYNC3 (without
Sign) + HSYNCPARAM `signers="…"`.

### S1.7  Title and scope

**Location:** title (line 2), abstract (lines 47-79), introduction (lines
88-141).

**Description:** Title is "Signaling Zone Owner Intent". Body content
goes well beyond intent signaling — it specifies the entire
Agent-to-Agent communication framework (HELLO/BEAT, transport
negotiation, EDNS(0) options, eight defined operations, sequence
diagrams). The TODO explicitly flags this (TODO §"Scope / Title").

**Recommendation:** Two reasonable options:

1. **Rename to reflect actual scope** — e.g., "Multi-Provider
   Coordination Framework for DNS Zones". This is honest about what the
   doc does, but is a larger framing change.
2. **Split into two drafts** — keep this one focused on intent signaling
   (HSYNC3 + HSYNCPARAM + scenarios), and move Agent communication
   (HELLO/BEAT, transports, operations) to a companion draft.

Given Last Call timing pressure, option 1 is faster. Option 2 is the
cleaner long-term structure.

## S2 findings (significant)

### S2.1  The Combiner is introduced mid-document, after concepts that depend on it

**Location:** `## The Combiner` at line 362.

**Description:** The Combiner is the centerpiece of how unsigned zone
data and provider-contributed data merge into a signed zone. It is
introduced under `# Source of Truth` as a sub-section. By the time it
appears, the reader has already encountered "the zone owner", "the
Signer", "the Agent", "DNS Providers", and an end-to-end architecture
diagram — but no Combiner. The TODO flags this.

**Recommendation:** Promote the Combiner introduction to the Introduction
or the Terminology section. A two-sentence definition is sufficient at
that level; the detail can remain at line 362.

### S2.2  Auditor role is named but never specified

**Location:** absent. The implementation has `auditors` as HSYNCPARAM key
#7, but the draft mentions Auditors nowhere.

**Description:** Per the implementation, an HSYNCPARAM `auditors`
key-value lists auditor providers — analogous to `signers` and `servers`.
But the role of an "Auditor" is undefined in the draft. The TODO flags
this (TODO §"Structural rewrite (do first)" final bullet).

**Recommendation:** Add a new section `## The Auditor` (peer of `## The
Combiner` and `## The Agent`) covering purpose, inputs, outputs,
relationship to Combiner and Agents, expected behavior on disagreement.
Even a minimal first-cut definition is better than the current silence,
which leaves `auditors=` in HSYNCPARAM examples (when they exist) as a
mystery.

### S2.3  Section "DNS Provider Synchronization Scenarios" describes user stories using deprecated wire format

**Location:** lines 201-286, all five scenario subsections.

**Description:** Each scenario describes operations on "the HSYNC RRset"
using the single-RR model. With the two-RR rewrite, every scenario needs
to be re-examined to determine whether it operates on HSYNC3 (provider
on/off, identity, upstream), HSYNCPARAM (role assignment, NS management
policy), or both.

For example, "Coordinated NS Record Management" sets NSMgmt via — what?
HSYNCPARAM `nsmgmt`. But "Provider Transition Management" turns a
provider on/off — HSYNC3 State. The scenarios mix these levels without
distinguishing them today.

**Recommendation:** Rewrite each scenario to use the correct
record/field. The scenarios are pedagogically valuable and should be
kept, just made accurate to the new model.

### S2.4  Sub-bullet "Specify whether each provider should sign the zone" in Introduction

**Location:** line 104.

**Description:** Same issue as S1.6 but in the user-facing introduction
bullet list. The reader is told the HSYNC mechanism lets the zone owner
specify per-provider signing — but in the two-RR model, that's a list in
HSYNCPARAM, not a per-provider HSYNC3 field. The framing needs updating.

**Recommendation:** Update the Introduction bullet list to reflect that
per-provider signing intent is expressed by inclusion in HSYNCPARAM
`signers=…`, not by a per-record flag.

### S2.5  Use-case for State=OFF assumes a single record type

**Location:** lines 502-526, `## Semantics of the HSYNC State Field`.

**Description:** The State semantics ("ON" = active provider, "OFF" =
being offboarded) live in HSYNC3 in the implementation. The
offboarding-via-State=OFF mechanism still makes sense in the two-RR
model, but the section text uses "HSYNC record" and "HSYNC RRset"
throughout.

**Recommendation:** Rename to `## Semantics of the HSYNC3 State Field`
and update prose. The semantics are unchanged; only the record name
needs adjustment.

### S2.6  Source of Truth section uses plural "sources of truth"

**Location:** lines 316-353.

**Description:** The phrase "Source of Truth" is conventionally singular,
denoting *the* authoritative origin of a piece of data. The draft uses
it as plural: "the source of truth is further split up into three
participants". This is conceptually fine, but the phrasing creates a
small stumble. The TODO flags this.

**Recommendation:** Rename the section to something like "Authoritative
Source per Data Class" or "Allocation of Authoritative Sources". Or
restructure the prose to say each participant is the authoritative
source for *its own data class* (and there is no global single source of
truth).

### S2.7  Agent "Integrated vs Separate" framing presents two options as equally valid, then uses only one

**Location:** `# The Agent: Integrated Signer vs Separate Agent` lines
288-314.

**Description:** The section says "in this document the functional
separation using a distinct Agent is used for clarity, not as a
statement on preferred implementation choice." The rest of the document
then writes as if the separate-Agent model is the model. The TODO flags
this; current text is fine for the framing but the reader is left to
notice the asymmetry.

**Recommendation:** Add one sentence at the end of the section: "The
remainder of this document writes as if the Agent is a separate
component; references to 'the Agent' in subsequent sections apply
equally to an integrated Agent function inside a nameserver or signer."

### S2.8  Multi-signer "consistency" claim is asserted but not enforced

**Location:** lines 112-114.

**Description:** The Introduction claims "By publishing this information
in the DNS, zone owners ensure all providers receive consistent
configuration information." The TODO flags this. The claim is too strong:
DNS publication does *not* guarantee consistency — providers receive
zone transfers asynchronously, and an adversary intercepting unsigned
zone transfers (acknowledged later in Security Considerations) can
disrupt this.

**Recommendation:** Soften to "...all providers eventually converge on
the same configuration information, modulo zone-transfer propagation
delays and the integrity of the zone-transfer path itself (see Security
Considerations)."

### S2.9  No specification of what happens when HELLO never completes

**Location:** `## The Initial HELLO Phase` lines 788-798 and following.

**Description:** The HELLO exchange between two Agents establishes
secure communication. The text says "If, however, this fails for some
reason, it should fall back to DNS-based HELLO." but does not specify:

- Timeout for an outstanding HELLO.
- Behavior when neither party can complete HELLO (network split,
  misconfiguration, etc.).
- Effect on other zones served by the same Agent pair.

The TODO flags this.

**Recommendation:** Add a paragraph specifying minimum timeout (e.g., 30
seconds), retry policy, and the operational effect of permanent HELLO
failure (which is: the zone enters a "synchronization-blocked" state and
should be flagged for operator attention).

### S2.10  Discovery has no failure mode if any DNS record is missing

**Location:** `### Locating a Remote DNS Transport Agent` lines 664-729
and the parallel API section.

**Description:** The discovery steps say "Lookup and DNSSEC-validate URI
record"; "Lookup and DNSSEC-validate SVCB record"; etc. The text does
not specify what happens if any of these records is missing or fails to
validate. The TODO flags this.

**Recommendation:** Add explicit failure handling: "If any of the
required records (URI, SVCB, JWK) is missing or fails DNSSEC validation,
discovery for this Agent fails. The Agent SHOULD log this and SHOULD
retry discovery on a subsequent zone refresh."

### S2.11  Specifying KEY as "legacy" fallback without explaining the threat model

**Location:** lines 687-691, lines 1124-1127.

**Description:** "If no JWK record is found, fall back to looking up and
DNSSEC-validating the KEY record". The text describes KEY as the legacy
mechanism, but doesn't explain *why* JWK is preferred. A reader needs to
understand whether falling back to KEY is safe in their environment or
not.

**Recommendation:** One sentence on the difference: KEY enables SIG(0)
signature verification only; JWK additionally enables HPKE encryption,
which protects payload confidentiality. KEY-only deployments lose
confidentiality but retain authenticity.

## S3 findings (polish)

### S3.1  `# Rationale` section is marked for removal

**Location:** lines 1234-1260.

**Description:** "TO BE REMOVED BEFORE PUBLICATION: # Rationale". The

### S3.2  Title for "Limitation of Scope for HSYNC-based NS Management" is verbose

**Location:** line 544.

**Description:** The subsection heading is long. The content is one
specific clarification: NS management does not include in-bailiwick

**Recommendation:** Rename to something shorter like "NS Management
Scope" or "In-Bailiwick Address Records Excluded".

### S3.3  Repeated "DNS Provider" capitalization is inconsistent

**Location:** throughout — sometimes "DNS Provider", sometimes "DNS
provider", sometimes "provider".

**Description:** The Terminology section (line 153) uses "provider"
(lowercase). Most body prose uses "DNS Provider" (capitalized). Sentences
about Agents/Combiners use "DNS providers" (lowercase plural). No clear
convention.

**Recommendation:** Pick one convention (probably "DNS Provider" as a
defined term, capitalized) and apply consistently.

### S3.4  Acknowledgments are missing

**Location:** absent. -01.md has no `# Acknowledgments` section.

**Description:** -00.md also has no Acknowledgments — this is a
pre-existing gap.

**Recommendation:** Add an Acknowledgments section before the change
history. Even if just a placeholder for now.

### S3.5  Sequence diagram has a layout artifact

**Location:** lines 1076-1111.

**Description:** The sequence diagram is generally good but has one
visual artifact at line 1101 (`OPT(beat) |`) that is missing an arrow
character on the line continuation. Probably a copy-paste leftover from
a previous revision.

**Recommendation:** Reformat the line. Minor.

### S3.6  Multiple references to `{{!RFC8901}}` not actually in references

**Location:** RFC 8901 is cited multiple times (lines 71, 516, 1227) but
the YAML references block (lines 42-45) is empty.

**Description:** kramdown-rfc auto-resolves these, so this is not
functionally broken. The convention in your other drafts (alg-split,
delegation-mgmt-via-ddns) is to *not* add explicit stanzas for RFC cites
and let auto-resolution handle them. This draft is consistent with that.
No action needed unless you want to standardize.

### S3.7  "Provider-Synchronization" name is a mouthful

**Location:** EDNS(0) option name, used throughout.

**Description:** "Provider-Synchronization EDNS(0) Option" reads slowly
and is repeated dozens of times. Compare to e.g. "Cookie" (one word) or
"Client Subnet" (two words).

**Recommendation:** Consider a shorter name. Candidates: "ProvSync",
"AgentSync", "PSYNC". This is a paint-the-bikeshed call; if you like the
current name, leave it.

### S3.8  Operations registry includes Mnemonic column but EDNS option spec doesn't reference it

**Location:** IANA registry table line 1349-1361 has a "Mnemonic" column.

**Description:** The body of the spec uses operation names ("HELLO",
"BEAT", etc.) without distinguishing operation *code* from operation
*mnemonic*. The Mnemonic column suggests they are different things, but
the body uses them interchangeably.

**Recommendation:** Clarify in the EDNS(0) option section that operation
numbers are the wire encoding, mnemonics are the presentation format.
Or drop the Mnemonic column and use names directly throughout.

### S3.9  The `## Defined Operations` section is the largest new addition in -01 but is not in -00 abstract

**Location:** -01.md lines 938-1032.

**Description:** -01 added 8 operation definitions (~100 lines new
content), but the abstract (carried over from -00) doesn't reflect this
expansion.

**Recommendation:** Update the abstract to mention the operations
registry and the eight defined operations, or generalize the abstract to
cover "agent-to-agent operation codes" without enumerating.

## Cross-cutting observations

### CC.1  The TODO file is mostly correct but misses key impl-level details

The pre-publication TODO at `drafts/TODO-2026-06-04.md` lines 362-464 is
broadly accurate. It correctly flags the HSYNC → HSYNC3+HSYNCPARAM
rewrite, the missing Auditor definition, the Combiner placement issue,
the "consistency" overclaim, and the HELLO/BEAT details. It misses:

- The `pubkey` and `pubcds` HSYNCPARAM keys (4 and 5 in the
  implementation) which are operationally important per the sister
  draft.
- The need for a new IANA registry for HSYNCPARAM keys.
- The `prefix`/`suffix` mismatch (TODO says `prefix`, implementation has
  `suffix`).

The TODO's effort estimate ("very large, ~50-70%+") still feels right.
Probably more than 70% if all S1 and S2 items are addressed.

### CC.2  Datatracker has -00; working tree has -01 not yet committed

Same pattern as delegation-mgmt-via-ddns earlier today. The published
-00 is significantly behind the working -01. Submission of -01 as a new
revision is straightforward once content is ready; no slug change needed.

### CC.3  Multi-author draft — sequence of edits needs coordination

The author list has four names (Leon Fernandez, Erik Bergström, Johan
Stenstam, Steve Crocker). A rewrite of this scale will need agreement
across authors. Suggest landing the high-priority restructure (S1.1
through S1.6) in a single PR with all authors notified for review.

### CC.4  Cross-references with delegation-mgmt-via-ddns-02 need to be added

Once HSYNCPARAM and the `pubkey` key are defined in this draft, an
informative reference back to `?I-D.ietf-dnsop-delegation-mgmt-via-ddns`
in the `pubkey` key definition section would close the cross-reference
loop. The motivating use case for `pubkey` is the SIG(0) bootstrap, and
that document is its specification.

### CC.5  Acknowledgments and editorial pass deferred to final prep

Per the convention from delegation-mgmt-via-ddns work, S3 items (and
also the Rationale removal in S3.1) are best handled in a final-prep
pass once content is settled. Don't burn time on them now.

## Suggested order of attack

Given Last Call ambitions for the sister drafts, the highest-leverage
work order is:

1. **S1.1 + S1.2 + S1.3 + S1.5 + S1.6**: the HSYNC → HSYNC3+HSYNCPARAM
   rewrite, including the HSYNCPARAM key definitions and the IANA
   registry. This unblocks the delegation-mgmt-via-ddns cite.
2. **S1.4**: Reserved/private use range — small addition, fits with the
   above.
3. **S2.2 (Auditor)**: needed for HSYNCPARAM `auditors` to mean
   anything.
4. **S2.1 (Combiner placement)**: cheap structural fix that aids
   readability of everything above.
5. **S2.3 + S2.4 + S2.5 + S2.6**: rewrite of scenarios, intro bullets,
   State semantics, Source of Truth.
6. **S2.7 through S2.11**: smaller technical clarifications.
7. **S3.x**: final-prep polish.

Items 1-2 are the critical path for the delegation-mgmt-via-ddns Last
Call dependency. Items 3-4 are next most valuable. Items 5-7 are
quality-of-spec improvements that can be batched into later PRs.
